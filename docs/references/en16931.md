# EN 16931 — European semantic standard for e-invoicing

## What it is

`EN 16931` is the CEN standard that defines the **semantic data model** of a
core electronic invoice for the European Union. It was mandated by
**Directive 2014/55/EU** on electronic invoicing in public procurement and
is the common denominator that every conforming syntax (Factur-X, UBL,
PEPPOL BIS, …) must express.

Public administrations in the EU are required to be able to **receive and
process** invoices that comply with the core model.

## Standard structure

| Part           | Content                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------- |
| EN 16931-1     | Semantic data model of the core invoice — fields, cardinalities, business rules (`BR-*`)         |
| EN 16931-2     | List of syntaxes that conform to the core model                                                   |
| EN 16931-3-2   | Syntax binding to **OASIS UBL 2.1**                                                               |
| EN 16931-3-3   | Syntax binding to **UN/CEFACT CII D16B** (Cross Industry Invoice)                                 |
| EN 16931-5     | Guidelines for extension methodology (CIUS and extensions)                                        |
| EN 16931-6     | Test methodology                                                                                  |

Biannual revisions are published by **CEN TC 434**. Validation artefacts
(XSD + Schematron) are distributed through the public
[ConnectingEurope/eInvoicing-EN16931](https://github.com/ConnectingEurope/eInvoicing-EN16931)
repository.

## Two supported syntaxes

Every conforming document must be expressed in one of:

1. **UBL 2.1** `Invoice` or `CreditNote` (OASIS)
2. **UN/CEFACT CII** `CrossIndustryInvoice` (D16B, backward-compatibly
   extended by D22B in recent Factur-X releases)

Both bindings map the same semantic BT/BG (Business Term / Business Group)
identifiers to concrete XML elements.

## Mandatory invoice fields (selected BT)

- `BT-1` — Invoice number
- `BT-2` — Invoice issue date
- `BT-3` — Invoice type code (UN/ECE 1001)
- `BT-5` — Invoice currency code (ISO 4217)
- `BT-27` / `BT-44` — Seller / Buyer name
- `BT-109` — Invoice total amount **without VAT**
- `BT-110` — Invoice total VAT amount
- `BT-112` — Invoice total amount **with VAT**
- `BT-115` — Amount due for payment

Each `BT-*` is constrained by one or more `BR-*` business rules (e.g.
`BR-CO-10` enforces that `BT-106 = Σ(BT-131)` — sum of invoice line net
amounts).

## Implementation notes for `einvoice-rs`

- `crates/core` models the **semantic** layer. Its `Invoice`, `Party`,
  `LineItem` types should carry the information required by the BT/BG
  identifiers above.
- Validation (business rules, BR-*) lives in an `InvoiceValidator`
  implementation that is shared by the Factur-X and UBL serializers.
- Do **not** embed syntax-specific concerns (XML namespaces, UBL extension
  points) in `einvoice-core`. Those belong to `einvoice-facturx` and
  `einvoice-ubl`.
